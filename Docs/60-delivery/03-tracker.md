## How to use this

| Column | Meaning |
|---|---|
| **ID** | Stable identifier, matching the owning module spec's open-work table |
| **Item** | What needs to exist |
| **Mod** | Owning module (`20-modules/`) |
| **Ph** | Roadmap phase |
| **Pri** | P0 blocks the phase · P1 required for the phase · P2 desirable |
| **Status** | `TODO` · `IN PROGRESS` · `BLOCKED` · `DONE` · `N/A` |
| **Owner** | Named individual — `—` means unassigned, which is itself a tracked problem |
| **Exit** | The objectively verifiable condition for `DONE` |

**Rules.** An item is `DONE` only when its exit condition is verifiably met. "Code written" is not `DONE`. `BLOCKED` requires a named blocker. An unassigned P0 is escalated at every review.

**The live-call-site rule (AU-2, added 2026-08-31, after `Docs/60-delivery/04-end-to-end-audit-2026-08-30.md` found 17 DONE rows — six P0 — were unreachable dead code that passed its own unit tests):** whenever a row's exit evidence asserts that a module, function or endpoint is "wired", "reachable", "live", "called from", or otherwise part of a real request/event path, that evidence must name a concrete `file:line` call site that is itself reachable from one of the running application's real entry points — not merely state that unit tests pass or that the module/file exists. "Reachable from a real entry point" means transitively imported (or, for a scheduled/event path, invoked) from one of the five processes named by the `ENTRY_POINTS` dict in `tests/test_reachability_gate.py`: `aida.main` (FastAPI app), `aida.workflows.worker` (Temporal worker), `aida.workflows.scheduler` (fleet scheduler), `aida.projectors.graph_projector` (Kafka consumer) and `aida.projectors.outbox_publisher` (Kafka producer) — re-check that list in the test file itself before citing it, since it is the authority, not this paragraph. Two exceptions must be stated explicitly when invoked, not assumed: (a) module-level reachability (import graph, what the gate above enforces) is a *necessary but not sufficient* condition — a row claiming a *specific function* is live needs a call site for that function, not just proof its containing module is imported by something on a live path (see AU-1's row, whose `ai_decision_lineage.py` example — module-reachable but its core function was not, before AU-5 fixed that — is exactly the case this distinction exists for); (b) a row legitimately blocked on infrastructure the test harness cannot provide (a live Kafka broker, a real IdP) may cite an in-process proof instead, but must say so explicitly rather than silently substitute a unit test for a live path. A row that cannot produce this evidence is not `DONE` — mark it `IN PROGRESS` or `TODO` with the real gap named, the same way `tests/test_reachability_gate.py`'s `ALLOWLIST` names the owning tracker row for every module it excuses. Future rows written by any session should be checked against this rule before being marked `DONE`.

A review item and a module item can describe the same work from two directions — `N7` (build an
ABAC engine) and `PG-7` (module 17 needs a policy decision point) are the same thing. Where that
happens the row names both, rather than being listed twice.
