Method: navigated every screen in both UIs, captured full-viewport screenshots, read each screen's DOM/accessibility tree, checked the browser console and network requests for errors. September 3, 2026.

Bottom line

The gap you're feeling isn't a design-quality gap — it's a broken wire. The React rebuild (ui-next) is not sending the identity header the backend requires, so every screen that loads real data fails with a red "could not be loaded" box. The legacy portal, hitting the exact same backend, works perfectly and returns real rows — proving the backend and the data are fine. Once that one header is added, the new UI should work like the old one does. Separately, the React rebuild is a deliberate work-in-progress: 7 whole feature areas the legacy portal has (Administration, AI governance, Context products, Enterprise control center, Tool registry, Transformations, Unified lineage) haven't been ported over yet — that's the second, bigger reason it currently looks thinner than "what the other vendor did."

1. Critical bug: the new UI can't talk to its own backend

Every data-driven screen in ui-next (Catalog, Marketplace, Relationships, Review queue, Studio, AI registry, Lineage refusals, Audit ledger, Sources, Operations — 10 of 16 screens) shows the same error:

The catalog could not be loaded
X-Principal-Id is required in development mode

Network tab confirms it's a real 401, not a rendering bug:

GET /v1/organizations/00000000-0000-0000-0000-000000000001/catalog/rows?limit=100 → 401

Root cause: ui-next/src/lib/api.ts sends every request with only Accept / Content-Type headers — it never attaches X-Principal-Id (or X-Roles / X-Organization-Id). The legacy portal's ui/scripts/api.js does this on every single request:

function baseHeaders(principal="local-ui-admin") {
  return {"X-Principal-Id": principal, "X-Roles": roles,
           ...(state.organizationId ? {"X-Organization-Id": state.organizationId} : {})};
}

The React client's get() / postJson() / putJson() helpers were never given the equivalent. Compounding it: compose.yaml defaults VITE_USE_FIXTURES to 0 (line 314), so out of the box the new UI runs in live-API mode with this gap live — not fixture mode, where it would look fine.

This also explains the "Could not load organizations" message under the org picker in the sidebar on every screen — same missing header, same 401, on the /v1/me / organizations call.

Suggested fix (small, contained)

In ui-next/src/lib/api.ts, add a header helper mirroring the legacy one and spread it into the three request functions' headers, e.g. a dev-mode default of X-Principal-Id: "local-ui-admin" (matching what legacy hardcodes), sourced from an env var so it's a one-line swap when real OIDC auth is wired in. This is a same-shape fix to an already-solved problem — the legacy file is the reference implementation sitting right next to it.

3. Where it's a genuine polish gap (not just the bug)

Comparing the two "Home" screens side by side, independent of the data bug: legacy's home is a proper product landing page — hero copy, live counters, a governance/trust panel, coverage-by-business-area breakdown. The new shell's "Get started" screen is a bare 3-item checklist. That's a legitimate design gap the header fix won't close on its own.

To be fair to the new shell: its per-screen empty/error states (e.g. "Pick a datasource to see its history", "Pick a datasource to begin") are clean and consistent, and no screen threw an uncaught JS exception or console error in this pass — error handling itself is solid, it's just that everything routes to an error right now because of item 1.

5. Code fix — applied

Status: patched on your machine

Edited ui-next/src/lib/api.ts directly. Added an identityHeaders() helper mirroring legacy's baseHeaders(), and spread it into all three request functions (get, postJson, putJson — the only three fetch() call sites in the file). Verified with tsc --noEmit (clean) and a partial vitest run covering Ask/Quality/Relationships/Semantics/ReviewQueue/Sources screens (all passing, no regressions surfaced).

// ui-next/src/lib/api.ts, right after USE_FIXTURES:

const DEV_PRINCIPAL_ID = import.meta.env.VITE_DEV_PRINCIPAL_ID || "local-ui-admin";
const DEV_ROLES =
  import.meta.env.VITE_DEV_ROLES ||
  "PlatformAdmin,OrganizationAdmin,ProjectAdmin,MetadataAdmin,MetadataIngestor,DataAdmin,
   SemanticAdmin,DataSteward,ToolDeveloper,ToolConsumer,AgentDeveloper,Reviewer,
   MetadataReviewer,Auditor,Operations,Analyst,Viewer";

function identityHeaders(): Record<string, string> {
  if (USE_FIXTURES) return {};
  return { "X-Principal-Id": DEV_PRINCIPAL_ID, "X-Roles": DEV_ROLES };
}

// then, in get() / postJson() / putJson():
headers: { Accept: "application/json", ...identityHeaders() }

One deliberate design call worth flagging: this is not gated on import.meta.env.DEV (Vite's dev-build flag). Your default compose service serves a production Vite build on port 3001 against the same identity_provider=development backend — a dev-build-only gate would have silently done nothing on exactly the deployment you're testing. The real safety net is server-side: security.py's OIDC branch never reads X-Principal-Id at all, so this header is inert (not a leak) once you're running against a real identity provider.

What this means concretely for Atlas:

  1. Catalog rows need trust signals at a glance — add a certification/uncertified pill and a "profiled Xm/h/d ago" freshness indicator to each row in CatalogTable.tsx, the way Atlan's list/card view does. The data almost certainly already exists (certification status and profiling timestamps are core to a data catalog schema) — this is a display change, not a new backend capability.
  2. Marketplace should read as product cards, not a form-filtered table — owner, certification, freshness, and a one-click "Request access" button per card, mirroring Atlan's pattern. Worth checking whether MarketplaceScreen.tsx's current layout already does this once data loads, or renders as a plain list.
  3. Lineage is your potential differentiator, not your gap — the narrated, question-driven lineage screen (NarratedLineageScreen.tsx) is a more modern pattern than either competitor's static graph. Prioritize getting it working and visible over copying their graph-explorer look.
  4. Collaboration primitives are the one feature-level gap both competitors have and Atlas doesn't — @mentions, comment threads, or embedded documentation on an asset. Not urgent, but worth a backlog item if the goal is Atlan-style voluntary adoption rather than mandated use.

Net take

This isn't "the backend is good and the frontend team didn't try" — the React rebuild's error states, empty states, and code comments all show a deliberate, disciplined migration in progress. It's one specific integration wire (the identity header) left unconnected, plus an honestly-tracked backlog of screens still to port. Fix the header, and you'll have a much clearer, apples-to-apples view of how close the new UI actually is to competitive.
