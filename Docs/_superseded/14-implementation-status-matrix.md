# 14 — Implementation Status and Decision Register

## Purpose

This is the single status source for what is implemented, partially implemented, pending, requires retesting, or requires a bank decision. Detailed design remains in documents 01–13; material completion evidence is append-only in `10-accomplishment-log.md`.

## Status definitions

| Status | Meaning |
|---|---|
| Implemented | Code, migration, API/runtime path, automated checks, and local end-to-end evidence exist. |
| Partial | A safe production-oriented vertical slice exists, but named breadth or certification remains. |
| Pending | Planned capability has not been implemented. |
| Retest required | Implemented locally but requires bank-scale, security, recovery, or target-environment certification. |
| Bank decision | Implementation must remain fail closed until an enterprise standard or policy is supplied. |

## Architecture decisions

| ID | Decision | Rationale | Revisit trigger |
|---|---|---|---|
| D-001 | Do not place LangGraph or Google ADK in the core | The core state, permissions and evidence must remain portable and deterministic | Add an adapter only when a specific approved workflow needs its checkpoint or ecosystem features |
| D-002 | Use a hybrid deterministic/LLM architecture | Models can interpret or propose; deterministic services authorize, validate, execute and audit | Never revisit the authority boundary; only expand approved reasoning routes |
| D-003 | Temporal owns durable workflows | Retries, cancellation, recovery and long-running task histories require a workflow system | Revisit only through enterprise platform standardization |
| D-004 | Kafka distributes events; it is not workflow state | Event replay and durable process state have different failure semantics | No planned change |
| D-005 | PostgreSQL is authoritative | Neo4j/search/vector projections must be reproducible and cannot become hidden truth | Revisit only if an approved metadata system of record replaces it |
| D-006 | Every analytical execution uses one query gateway | Removes policy, masking, cost and evidence bypass paths | No planned change |
| D-007 | Raw source values, questions and feedback comments are not platform memory | Minimizes regulated data replication and model-context leakage | Expand only with classification-specific retention approval |
| D-008 | Model-route approval does not activate model execution | Governance intent, deployment selection, credential resolution and adapter registration are independent controls | No planned change; readiness requires every control |
| D-009 | Graph exploration is lazy, bounded and value-free | A browser must not download an enterprise graph or regulated row values; server policy caps depth/nodes/edges and returns explicit truncation evidence | Raise limits only after bank-scale performance and privacy certification; add a virtualized rendering adapter without changing the API safety boundary |
| D-010 | Prompt-risk screening occurs before retrieval or model/tool planning | Malicious instructions must not influence retrieval, enter model context or select an execution path; only classifier version, score and reason codes are retained alongside the existing question HMAC | Add approved semantic/ML classifiers only as defense in depth; deterministic deny rules and downstream execution gates remain authoritative |
| D-011 | Quality baselines remain value-free and source freshness is explicit | Counts, rates and fingerprints can support reproducible controls without replicating regulated rows; metadata scan time cannot prove when source business data changed | Enable source freshness only through an approved connector watermark, classification and retention contract |
| D-012 | Pull, push and future stream ingestion converge on one versioned metadata envelope | A common authoritative persistence path prevents connector-specific identity, drift, privacy and projection behavior; datasource locks plus idempotency make retries deterministic | Evolve only through backward-compatible envelope versions and schema-registry compatibility policy |

## Decisions required from the bank

These do not block continued product development, but they block production release: identity provider and claim contract; policy engine; secret manager; source priority and versions; network zones and regions; data residency and retention; RPO/RTO; model provider/routes; SIEM and WORM archive; Kubernetes/managed-service standards; LOB isolation and chargeback model.
