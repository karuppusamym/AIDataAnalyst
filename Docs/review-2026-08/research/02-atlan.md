# Atlan Competitive Teardown — August 2026

## Verdict in five lines

Atlan is genuinely good at: a proven, extensible typed-metadata model inherited from Apache Atlas; a two-plane access-control idea (catalog/metadata policies vs. data-query policies) wrapped in tag-based ABAC (Purposes) that is more precise than most catalogs attempt; OpenLineage-native lineage ingestion; and — as of 2025–2026 — being first to wire an MCP server and an agent-facing API directly into a governance catalog. It is genuinely bad at: pricing transparency, a confusing Personas/Purposes UI in practice, automation (Playbooks) that lacks undo/event-triggers/impact-reports, an architecture story (Iceberg "Context Lakehouse") that doesn't reconcile with its documented Cassandra/Atlas backend, and DQ Studio still not GA. The two things worth copying outright: (1) the metadata-policy vs. data-policy separation of concerns, and (2) exposing governed metadata to agents through a scoped, tool-based protocol (MCP) with a metadata-only-to-LLM boundary — both map directly onto what a bank-internal governed AI data-analyst platform needs, and both should be built more conservatively and more auditable than Atlan currently ships them.

## 1. Positioning 2026

Atlan's brand line is now **"The Context Layer for AI"**, reframing the product from data catalog to AI infrastructure — a shift documented across its own knowledge base ([AI Platform Architecture: Control Plane and Context Layer](https://atlan.com/know/ai-agent/ai-platform-architecture/), [AI Control Plane: Components, Architecture and Use Cases](https://atlan.com/know/ai-control-plane/)). Atlan is named a **Leader in the 2026 Gartner Magic Quadrant for Data & Analytics Governance Platforms**, moving up from "Visionary," with Gartner citing "metadata lakehouse architecture, ecosystem-led innovation, and [reported] 415% customer growth" ([atlan.com/know/gartner/magic-quadrant-for-data-governance-2026](https://atlan.com/know/gartner/magic-quadrant-for-data-governance-2026/)); Atlan also claims Leader status in the **Forrester Wave for Data Governance, Q3 2025**. Named reference customers include General Motors, Nasdaq, Unilever, Autodesk, Virgin Media O2.

Editions are not clearly published as a self-serve price list (no public "Essentials/Growth/Enterprise" page was found on atlan.com — pricing is quote-based). Third-party pricing trackers estimate roughly **$20K–$50K/yr for small teams, up to $120K–$300K+/yr for large enterprise deployments**, with per-user list costs of $1,000–$2,500/user/yr, plus implementation ($5K–$50K+) and per-connector costs — treat as directional, non-primary-source estimates ([Vendr marketplace listing](https://www.vendr.com/marketplace/atlan)). Atlan raised **$105M** in 2024, valuing it at ~$750M, funding its push into AI/governance ([Atlan's $105M raise](https://atlan.com/atlan-raises-105m-funding/)).

The 2025–2026 platform is bundled around: core catalog/discovery, governance (Personas/Purposes, Playbooks, Contracts), Data Products/Data Mesh, Data Quality Studio (new, private preview for Snowflake mid-2025, then Databricks), Atlan AI, an App Framework/Marketplace, and the Atlan/Remote MCP Server — sold together as the "Context Layer" / "metadata lakehouse."

**Take/Leave:** Don't copy the "Context Layer for AI" branding or take the architecture claims at face value; do copy the strategic bet — position the platform as agent-facing infrastructure (MCP/API-first) from day one rather than bolting AI onto a human-browsing UI later.

## 2. Metadata model

**Apache Atlas heritage is explicit and substantial.** Atlan states it "runs a hardened fork of Apache Atlas as its metadata backend, extended with 100+ cloud-native connectors" and that operational differences vs. open-source Atlas are about *managed infrastructure*, not a type-system rewrite ([Atlan vs Apache Atlas](https://atlan.com/atlan-vs-apache-atlas/)). Persistent datastores cited: **Cassandra, Elasticsearch, PostgreSQL** (backups: 24-hr RPO, daily); orchestration via Kubernetes (Loft Virtual Clusters) and Argo Workflows for CI/CD.

**Type system**: everything is a typed instance under a common supertype — "Every asset in Atlan — a table, a column, a dashboard, a dbt model — is an instance of a type… Most types inherit from **Asset**, which carries attributes shared across all metadata objects: name, description, owners, classifications" ([Typedefs reference](https://docs.atlan.com/product/capabilities/build-apps/references/types)). The reference nav groups types as Core, Catalog, BI, Data Processing, Agentic, AI — i.e., BI dashboards/reports, dbt models/tests/sources, and AI/agent-related asset types are first-class typedefs alongside SQL assets. Custom typedefs, custom relationship types, and **custom metadata** ("structures" of typed attributes attachable to assets, colloquially the old Atlas "business metadata"/badges) are creatable via the [Typedef toolkit](https://developer.atlan.com/toolkits/typedef/) and pyatlan's `CustomMetadataDef` ([how-to](https://docs.atlan.com/product/capabilities/build-apps/sdks/python/custom-metadata/how-tos/create-custom-metadata)), including enumerations ([manage options](https://docs.atlan.com/product/capabilities/build-apps/sdks/python/custom-metadata/how-tos/manage-enumerations)).

**Asset hierarchy**: Connection → Database → Schema → Table/View → Column is the SQL spine; BI assets (Tableau/Power BI/Looker workbooks, dashboards, reports, fields) and dbt assets (sources, models, seeds, tests) attach via lineage and relationship typedefs rather than the SQL containment tree.

**Glossary ("Business Graph")**: three-tier — **Glossary → Category (with subcategories) → Term**, the Term being "the lowest unit unique to each glossary." Terms carry six relationship types: related, synonyms, recommended, antonyms, translated, and reciprocal classifies/classified-by ([What is a Glossary](https://docs.atlan.com/product/capabilities/governance/glossary/concepts/what-is-a-glossary)). Terms attach to assets and are filterable on the Assets page, explicitly framed as making "people and agents read data the same way."

**Domains & Data Products (Data Mesh)**: Domains/sub-domains organize assets for federated ownership; **Data Products** are curated, published bundles created either through a dedicated Products module or directly from the lineage graph. Creation requires admin-enabled domain policies; fields include name (≤80 chars), required domain, description, **Criticality** (High/Medium/Low), **Sensitivity** (Public/Internal/Confidential), owners, and **Visibility** (domain-only / selected members / org-wide). Assets are added via manual browse-and-select or rule-based filters (connection, certification, tags, terms); **output ports** determine cross-product/cross-domain business lineage, with input ports auto-displayed. Products progress Draft → Published → Sunset → Archived, and carry a README ([Create data products how-to](https://docs.atlan.com/product/capabilities/data-products/how-tos/create-data-products), [Data Products concept](https://docs.atlan.com/product/capabilities/data-products/concepts/what-are-data-products), [Managing data products (pyatlan)](https://docs.atlan.com/product/capabilities/build-apps/sdks/python/data-mesh/how-tos/manage-data-products), demo: [Data Products & Domains: Create a Data Product](https://atlan.com/demos/create-a-data-product/)).

**Take/Leave:** Replicate the typed-entity/supertype model and the custom-metadata attribute framework wholesale — it is a proven, extensible pattern with 10+ years of Atlas lineage behind it; do not inherit the Atlas-era storage stack (Cassandra/JanusGraph-class ops burden) — build the graph on a modern, better-operated store. The Domain → Data Product model is worth replicating for a bank's line-of-business ownership structure, but tighten Sensitivity/Criticality into machine-enforceable fields (tied directly to access policy) rather than descriptive-only metadata.

## 3. Architecture

Public/inferable architecture split cleanly into an **"old" heritage layer** (Atlas fork + Cassandra + Elasticsearch + Postgres, per the Atlas-comparison page above) and a **new marketing narrative, "Context Lakehouse,"** pushed hard through 2025–2026 ([Context Lakehouse](https://atlan.com/context-lakehouse/), [Metadata Lakehouse: Architecture & Implementation in 2026](https://atlan.com/know/metadata-lakehouse/)). Atlan's own description of the Context Lakehouse has four layers:
1. **Iceberg-native metadata store** — Apache Iceberg tables giving ACID transactions, schema evolution, time travel, queryable by Spark/Trino/DuckDB/Snowflake/BigQuery.
2. **Knowledge graph** — domains, lineage, policies, quality scores in "a single traversable graph," claimed sub-100ms access.
3. **Vector-native AI search** — every asset embedded for semantic retrieval "by meaning, not keywords, across billions of assets."
4. **Time travel & audit** — full historical state queryable for GDPR/CCPA/SOX.

Protocol support claimed: **MCP** (governed agent reads), **A2A** (agent-to-agent bidirectional writes), SQL-via-Iceberg, REST/Graph APIs with Python/Java/Node/Go SDKs. It is explicitly framed as an **active, real-time metadata plane**: "agents write observations, quality signals, and usage patterns back into the store — context compounds with every interaction." Notably, this Context Lakehouse copy makes **no mention of Cassandra/JanusGraph/Elasticsearch/Kafka** — Atlan is not publicly reconciling how/whether Iceberg replaces the Cassandra+ES Atlas-fork backend described elsewhere; treat this as unresolved marketing-vs-engineering tension worth probing in vendor due diligence.

**Tenant isolation**: Atlan states it achieves **single-tenant isolation in cloud environments** (per the Atlas-comparison page). For private/on-prem sources, Atlan uses a **"Secure Agent"** (outbound-only agent, TLS 1.2, AES-256 at rest, credentials never transmitted to Atlan, ISO 27001/SOC 2 aligned — [Secure Agent security](https://docs.atlan.com/secure-agent/references/security)) and, newer, a **Self-Deployed Runtime (SDR)** for connector apps running in the customer's own network via Docker Compose, Kubernetes, or an "SDR Orchestrator" that manages lifecycle across multiple connector apps ([Deployment options](https://docs.atlan.com/product/connections/self-deployed-runtime/concepts/deployment-options)). Cross-region private connectivity is supported via AWS VPC Lattice / PrivateLink patterns ([Cross-region private network connectivity](https://docs.atlan.com/platform/concepts/cross-region-private-network-connectivity), [Private connectivity with AWS VPC Lattice](https://docs.atlan.com/platform/concepts/private-connectivity/aws-vpc-lattice)) — directly relevant to a bank's network-isolation requirements. The **AI gateway** is a separately-described "centralized control plane" deployed multi-region (US/EU/APAC) on Kubernetes with per-tenant API keys/rate limits and PrivateLink/VPC-peering enforcement ([Atlan AI security](https://docs.atlan.com/product/capabilities/atlan-ai/concepts/security)).

**Take/Leave:** The "metadata as queryable data" (Iceberg) idea is worth stealing — it lets internal analysts and auditors run SQL directly over lineage/policy/history tables for compliance reporting instead of exporting from a proprietary API. The unresolved gap between marketed and documented backend is itself a lesson: don't let our own architecture docs diverge from what's actually running — for a regulated audience that gap is disqualifying, not cosmetic. Copy the Secure Agent / outbound-only, credential-never-leaves-network pattern directly; it is the right shape for bank network policy.

## 4. Discovery & search

Search supports structured/faceted filtering plus **conversational/natural-language search** via Atlan AI ([Search with conversational AI](https://docs.atlan.com/product/capabilities/discovery/how-tos/search-with-conversational-ai), [Structured search](https://docs.atlan.com/product/capabilities/discovery/how-tos/search-and-discover-assets), [Use filters menu](https://docs.atlan.com/product/capabilities/discovery/how-tos/use-the-filters-menu)).

**Asset profile page** (per [What are asset profiles?](https://docs.atlan.com/product/capabilities/discovery/concepts/what-are-asset-profiles)) has: an **Overview** (technical name/alias, row/column counts, connection, description, certification, owners, mini-lineage); **Lineage** tab (visual, exportable as CSV/image); **Related Assets** (cross-type links, e.g., BI reports feeding off a table); **Column/Field Preview**; **Sample Data** (admin-gated behind credential validation); **Linked Queries** (saved queries + run frequency); and a **README** tab for free-text "tribal knowledge." Right-sidebar tabs: Overview, Columns, Relations, Usage, Lineage, Fact-Dim Relations, Activity (changelog), Resources, Queries, Requests, Properties, Integrations, plus any custom-metadata tabs.

**Usage/Popularity**: computed from query-log mining across Snowflake, BigQuery, Redshift, Databricks, Tableau, Power BI over a rolling 30-day window. Popularity score formula: **`distinct_users × log(total_read_queries)`**, bucketed into 4 percentile tiers shown as 1–4 blue bars on asset cards; sidebar Usage tab shows top users, recent queries, read/write compute cost, and top-5 queries by Popular/Slow/Expensive ([Interpret usage metrics](https://docs.atlan.com/product/capabilities/usage-and-popularity/how-tos/interpret-usage-metrics)). Documented gaps: Redshift expensive-query/compute-cost data unavailable "due to limitations at source"; similar Databricks API constraints; Tableau Server + JWT auth unsupported; Databricks SQL masking (effective Aug 26, 2026) halts metric updates for masked columns ([Troubleshooting usage/popularity](https://docs.atlan.com/product/capabilities/usage-and-popularity/troubleshooting/troubleshooting-usage-and-popularity-metrics)).

**Take/Leave:** Copy the popularity-score formula and query-log-mining approach outright — cheap, high signal, no new infra. Build conversational/NL search with much stricter guardrails than Atlan appears to have from launch (reviewers report poor results on exploratory queries) — for a bank-facing tool, an NL search that silently returns wrong or partial results is worse than no NL search.

## 5. Lineage

Lineage is generated via a mix of **connector-native extraction** (warehouse query-log parsing — explicitly documented for BigQuery, Redshift via ["Mine Amazon Redshift"](https://docs.atlan.com/apps/connectors/data-warehouses/amazon-redshift/how-tos/mine-amazon-redshift), Databricks via ["Extract lineage and usage from Databricks"](https://docs.atlan.com/apps/connectors/data-warehouses/databricks/how-tos/extract-lineage-and-usage-from-databricks)), **dbt** ([what Atlan crawls from dbt Core](https://docs.atlan.com/apps/connectors/etl-tools/dbt/references/what-does-atlan-crawl-from-dbt-core)), and **OpenLineage** for Airflow and Spark (dedicated troubleshooting pages exist for both: [Airflow/OpenLineage](https://docs.atlan.com/apps/connectors/lineage/apache-airflow-openlineage/troubleshooting/troubleshooting-apache-airflow-openlineage-connectivity), [Spark/OpenLineage](https://docs.atlan.com/apps/connectors/lineage/apache-spark-openlineage/troubleshooting/troubleshooting-apache-spark-openlineage-connectivity), plus a generic OpenLineage ingester documented in [What Atlan crawls from Generic OpenLineage](https://docs.atlan.com/apps/connectors/lineage/generic-openlineage/references/what-does-atlan-crawl-from-generic-openlineage) and an [OpenLineage config/facets reference](https://docs.atlan.com/product/connections/references/openlineage-configuration-and-facets)). Atlan co-presented on this at Airflow Summit 2025 ("Activating operational metadata with Airflow, Atlan and OpenLineage" — [session](https://airflowsummit.org/sessions/2024/activating-operational-metadata-with-airflow-atlan-and-openlineage/)).

**Lineage graph UI** ([View lineage how-to](https://docs.atlan.com/product/capabilities/lineage/how-tos/view-lineage)): zoom in/out controls + minimap; a "refocus" button to reset to base asset; **expand/collapse** buttons per node plus "Expand all"; **"Find in canvas"** search; column-level lineage view with its own search/sort; hover **metadata popovers** (type, DB/schema, owners, usage, DQ status); toggleable process nodes and edge visibility; a **visibility slider** to filter assets off the primary path; **column-level impact** reachable via a "curved downward arrow"; a **"View impact"** button on popovers; exportable lineage reports (CSV/image — [Download and export lineage](https://docs.atlan.com/product/capabilities/lineage/how-tos/download-and-export-lineage)). Atlan AI can generate **natural-language explanations of lineage transformations** and be used interactively for lineage/impact analysis ([Use Atlan AI for lineage analysis](https://docs.atlan.com/product/capabilities/atlan-ai/how-tos/use-atlan-ai-for-lineage-analysis)). Custom/programmatic lineage is pushable via SDK/API (asset-to-asset "Process" typedefs), though the docs page fetched gave only high-level coverage of this path — worth deeper technical validation before a build.

Screenshots: [Lineage: Impact Analysis Through the UI](https://atlan.com/demos/impact-analysis-through-the-ui/), [Data Asset 360°](https://atlan.com/data-asset-360/), [Data Lineage on the Context Layer](https://atlan.com/data-lineage/).

**Take/Leave:** Adopt OpenLineage as our lineage ingestion standard wholesale rather than inventing a proprietary event format — it's an open spec with existing Spark/Airflow integrations, so building our own parser is wasted effort. Column-level lineage and an impact-analysis view are must-build-natively for a bank (change-risk and audit use cases), not a nice-to-have to defer.

## 6. Playbooks & automation

**Playbooks** = a rule-based bulk-metadata engine, admin-only ([Set up playbooks](https://docs.atlan.com/product/capabilities/playbooks/how-tos/set-up-playbooks)). UI flow: name (≤46 chars) + description/icon → **Build Rules** page with **Filters tab** (AND/OR "match all"/"match any" across connection, asset type, certification, tags, domains, dbt properties, usage metrics, etc.) and **Actions tab** → **Execution** screen (Run once, or Schedule hourly/daily/weekly/monthly with timezone). Supported bulk actions: certificates (Verified/Draft/Deprecated/none), descriptions, ownership (add/remove/replace), glossary terms, tags (ADD→REMOVE→REPLACE execution order), domain/sub-domain membership, and custom-metadata properties.

Documented limitations: **no undo** (must re-run a corrective playbook); can't run two playbooks concurrently on overlapping asset sets; tag propagation through lineage can lag behind playbook completion; **no per-asset impact report or email notification**; column profiling limited to numeric/text types only. Third-party review sources add: **no event-based triggers**, no advanced approval workflows in automation ([getcollate.io teardown](https://www.getcollate.io/learning-center/atlan-data-catalog)). Prior "Intelligent Automation" push (2022) framed similarly ([Introducing Supercharged Automation](https://humansofdata.atlan.com/2022/12/introducing-supercharged-automation/), [Intelligent Automation product page](https://atlan.com/intelligent-automation/)).

**Application SDK / Atlan Apps**: `atlanhq/application-sdk` is an open-source **Python library for building resilient apps on Atlan** — metadata crawlers (MySQL, Metabase reference implementations), OpenAPI loaders, custom extensions, shipped with Docker base images (`app-runtime-base`) for containerized deploys ([GitHub](https://github.com/atlanhq/application-sdk), [PyPI](https://pypi.org/project/atlan-application-sdk/3.20.2/), [Apps framework concept](https://docs.atlan.com/product/capabilities/build-apps/concepts/apps-framework)). In August 2025 Atlan launched the **App Framework** (private preview) — "turns the Metadata Lakehouse into a launchpad for innovation" — with standardized metadata/lineage/governance/collaboration APIs, secure app runtimes, SDKs/CLI/sandboxes, and UI extension points, plus **21 launch partners**: Alteryx, ALTR, Anomalo, Ataccama, Bigeye, BigID, Dagster, dbt Labs, Elementary Data, Great Expectations, Immuta, Lovelytics, Monte Carlo, Pantomath, Prophecy, Qualytics, Revefi, Sentra, Soda, Tavro, Trustlogix — apps to surface via an **Atlan Marketplace** ([Businesswire launch release](https://www.businesswire.com/news/home/20250812543551/en/Atlan-Launches-App-Framework-with-21-Leading-Partners-to-Make-Context-Shareable-Across-the-AI-Native-Enterprise); demo: [Apps Framework: An Introduction and Demo](https://atlan.com/demos/apps-framework-introduction/)).

**Take/Leave:** Copy the filter+action bulk-rule engine concept, but design out the gaps a bank's auditors won't accept: add undo/rollback, per-run diffs and impact previews, and event-based triggers from v1 — these are compliance requirements for us, not polish. The Application SDK / plugin-framework pattern is worth copying for extensibility, but keep the marketplace/partner-ecosystem ambition out of scope initially.

## 7. Governance

**Classifications/tags**: propagate through lineage (Atlas heritage — cf. [Apache Atlas Classification Propagation](https://atlas.apache.org/2.0.0/ClassificationPropagation.html)); demoed at [Tags: Tagging Through Propagation](https://atlan.com/demos/tagging-through-propagation/); third-party classification add-ons exist (e.g., [ALTR Data Classification for Atlan](https://altr.com/solutions/atlan/)).

**Data contracts**: a governance object to "define and track data quality expectations, SLAs, and data-sharing agreements between teams and systems," creatable via UI or SDK, with GitHub-based **impact analysis** for contract changes ([Contracts overview](https://docs.atlan.com/product/capabilities/governance/contracts), [Create data contracts](https://docs.atlan.com/product/capabilities/governance/contracts/how-tos/create-data-contracts), [Manage via SDKs](https://developer.atlan.com/snippets/datacontract/manage-via-sdks/)). Exact YAML schema fields were not retrievable from the fetched pages — pull the raw schema from `developer.atlan.com/snippets/datacontract/` before designing a governed-AI pipeline around it.

**Certificates**: Verified / Draft / Deprecated / none — settable manually or via Playbooks/SDK ([Add certificates](https://docs.atlan.com/product/capabilities/discovery/how-tos/add-certificates), [Certify assets (SDK)](https://developer.atlan.com/snippets/common-examples/certificates/)). **Announcements** exist as an asset-level broadcast mechanism ([Add and share announcements demo](https://atlan.com/demos/add-and-share-announcements/), [Asset Change Notification](https://docs.atlan.com/product/integrations/references/asset-change-notification)).

**Take/Leave:** Copy certificate states and lineage-based tag propagation directly — both are simple, high-value, low-risk patterns. Treat data contracts as a good idea implemented loosely by Atlan: design our schema as versioned and machine-enforceable (contract violation should be able to block a pipeline or flag an asset automatically), not just descriptive.

## 7a. Personas & Purposes — expanded treatment (the part worth studying most)

This is Atlan's most distinctive governance design and the one most directly transferable to a bank-internal platform, so it gets its own section.

**Personas** are team/role-scoped policy bundles: a persona attaches users/groups to a set of **metadata policies, data policies, business-graph (glossary) policies, and domain policies**, plus a custom catalog view (landing page, visible asset types, sidebar tabs, discovery filters). Membership grants/revokes access immediately; a user can belong to multiple personas, with effective access = the union of all assigned policies ([What are personas?](https://docs.atlan.com/product/capabilities/governance/access-control/concepts/what-are-personas), [Create a persona how-to](https://docs.atlan.com/product/capabilities/governance/access-control/how-tos/create-a-persona)). Structurally a persona editor is: pick connection(s) → scope assets via browse/search/rules → configure permissions — the same editor pattern is reused for both metadata and data policies, which is part of why reviewers find it confusing (two conceptually different policy types share one UI shape).

**Purposes** are the cross-cutting complement: instead of scoping by team, a purpose scopes by **tag**. Attach policies to a tag once (e.g., `PII`, `Confidential`, or a bank-specific tag like `MNPI`), and every asset carrying that tag — present or future — automatically inherits the purpose's policies, "regardless of which persona or team the user belongs to." An explicit deny set on a purpose is described as **"a hard ceiling"** that overrides even Admin role or connection-admin status ([What are purposes?](https://docs.atlan.com/product/capabilities/governance/access-control/concepts/what-are-purposes)). Enforcement primitives available to a purpose: **data masking** (`***` substitution in query results), **query denial**, and metadata-edit restriction.

**The precise, load-bearing distinction — metadata policies vs. data policies:**
- **Metadata policies** control who can view/edit/restrict *governance-layer* properties on an asset inside a persona: tags, terms, certification status, custom metadata, ownership, and other catalog attributes, plus related API operations. Docs are explicit that metadata policies **do not** govern data-quality rules, **do not** govern actual data querying/retrieval, and **do not** govern bootstrap permissions ([Metadata Policy docs](https://docs.atlan.com/product/capabilities/governance/access-control/metadata-policy)).
- **Data policies** are a structurally separate policy type inside the same persona that governs the operational layer — the actual querying and retrieval of data (e.g., through Atlan's Insights/query workspace, sample-data preview, export). They exist as a distinct object from metadata policies even though both are configured through a similar UI.

Why this separation matters for a bank: it lets an organization delegate **catalog stewardship** (who can certify a table, tag it PII, write its description, link it to a glossary term) to data stewards and business analysts **without** granting them any ability to query the underlying data — and conversely, grant a DBA or analyst **query access** without giving them authority to alter classification/certification metadata that drives downstream compliance reporting. This two-plane design maps cleanly onto a "catalog control plane vs. data access plane" split, which is exactly the boundary a governed AI data-analyst platform needs between "what the agent is allowed to know about the schema/lineage/policy" and "what the agent is allowed to actually query."

**What's still unclear from public docs** (a real gap, not just a documentation gap on our side): the fetched pages do not specify the exact **push-down mechanics** into native warehouse controls — i.e., whether an Atlan data policy compiles into a Snowflake row-access-policy/masking-policy or a Databricks Unity Catalog grant, or whether enforcement happens only inside Atlan's own query proxy/workspace (in which case ad hoc access via a native SQL client would bypass Atlan's data policies entirely). Atlan's Snowflake Horizon Catalog integration material gestures at this without confirming it precisely ([Snowflake Horizon Catalog + Atlan](https://atlan.com/know/data-catalog/snowflake-horizon-catalog-and-atlan/)). This is the single most important thing to confirm with an Atlan SE before assuming their model as a design reference for a bank, because "governance enforced only inside the catalog app, bypassable via direct warehouse access" is a materially different (and much weaker) security posture than "governance compiled into the warehouse's own RBAC."

**Take/Leave:** Take the two-plane separation (metadata/catalog policy vs. data/query policy) and the tag-based ABAC "hard ceiling" override pattern (Purposes) as core design inputs — they are the right conceptual shape for regulatory tags like PII/MNPI that must apply irrespective of team or role. Leave — i.e., do not replicate — enforcing data policy only inside an app-layer gateway: for an audited bank environment, data-access policy should compile directly into the warehouse's native RBAC/RLS/masking (Snowflake row access policies, Databricks Unity Catalog) so there is one source of truth an auditor can inspect, with the catalog as the authoring/observability layer rather than the sole enforcement point.

## 8. AI / agents (2025–2026)

**Atlan AI** is described as "the intelligence layer of the Enterprise Context Layer: agents that build, maintain, and activate enterprise context at scale" ([What is Atlan AI](https://docs.atlan.com/product/capabilities/atlan-ai/concepts/what-is-atlan-ai)). Capabilities: auto-generated descriptions for tables/views/columns/terms/categories; AI overviews for glossaries/categories; natural-language lineage-transformation explanations; auto-suggested DQ rules; conversational/NL search. Guardrails: every AI suggestion is accept/reject/edit by the user, changes are tagged "Updated using Atlan AI" in the activity log, editing still requires normal edit permissions, and conversational AI is gated by feature flag + explicit admin approval. Architecture: "multi-model, routed through a centralized AI gateway supporting multiple LLM providers" — specific model names undisclosed. Data-handling claim: **no raw customer data sent to AI providers, only metadata** (names/descriptions/lineage SQL/asset names/glossary context); metadata/prompts/outputs are **not used to train foundation models**; a 30-day AI-observability retention window is used only for quality monitoring ([Atlan AI security](https://docs.atlan.com/product/capabilities/atlan-ai/concepts/security)). GA/beta boundaries are not crisply published in the docs pulled — "additional enablement or licensing" language suggests a mix of GA and gated features; verify per-feature status directly with Atlan for a procurement decision.

**Atlan MCP Server** (`atlanhq/agent-toolkit`, open source): exposes tools including `search_assets`, `get_assets_by_dsl` (DSL-based advanced/similarity search), `traverse_lineage`, `update_assets` (descriptions, certificate status), `create_glossaries` / `create_glossary_categories` / `create_glossary_terms`, `create_dq_rules` / `update_dq_rules` / `schedule_dq_rules` / `delete_dq_rules`, and `query_asset` (execute SQL against a table/view asset) ([README](https://github.com/atlanhq/agent-toolkit/blob/main/modelcontextprotocol/README.md), [PyPI atlan-mcp-server](https://pypi.org/project/atlan-mcp-server/0.1.0/), [awesome-mcp listing](https://mcpservers.org/servers/atlanhq/agent-toolkit)). Auth: `ATLAN_API_KEY` + `ATLAN_BASE_URL` + optional `ATLAN_AGENT_ID` env vars (i.e., a standard Atlan personal/service API token — access control is whatever that key's persona/purpose grants, so MCP calls inherit the same Personas/Purposes RBAC/ABAC). Transports: **stdio** (default, local/IDE), **SSE** (recommended for remote/production), **streamable-http** (Kubernetes); `RESTRICTED_TOOLS` env var lets an admin blocklist specific tools for a deployment. Containerized via `ghcr.io/atlanhq/atlan-mcp-server:latest`. Atlan's own material additionally describes a **"Remote MCP server"** exposing the "Enterprise Data Graph" to Claude, ChatGPT, Cursor, Gemini, and **Snowflake Cortex**, plus native **A2A (agent-to-agent)** protocol support for bidirectional writes back into the context store ([blog announcement](https://blog.atlan.com/announcements/atlan-mcp-ai-metadata/), demo: [MCP Server: An Introduction and Demo](https://atlan.com/demos/mcp-introduction/), [Building a Production Ready AI Analyst demo](https://atlan.com/demos/building-production-ready-ai-analyst/)). Note the `query_asset` tool is a meaningful capability/risk for a bank: it lets an MCP-connected agent execute live SQL through Atlan against a table asset, not just read metadata — access-scoping via Purposes/tags becomes the critical control surface.

**Take/Leave:** Take the metadata-only-to-LLM boundary and the human-in-the-loop accept/reject UX for AI-generated content as non-negotiable defaults — both are exactly right for a bank. Take the MCP-as-agent-interface architecture generally. Leave the `query_asset`-style tool as designed (an MCP tool that runs live SQL, scoped only by whatever policy the caller's API key happens to carry) — for a first release, either omit a live-query tool entirely or wrap it in an additional, explicit per-query approval/allowlist layer independent of the catalog's general access policy, since MCP tool calls are an easy path for scope creep and prompt-injection-driven overreach.

## 9. Developer surface

- **pyatlan** (`atlanhq/atlan-python`) — official Python SDK, actively maintained on PyPI ([GitHub](https://github.com/atlanhq/atlan-python), [PyPI](https://pypi.org/project/pyatlan/), [docs site](https://atlanhq.github.io/atlan-python/)); covers typedefs/custom metadata, relational assets, glossary, access control (personas/purposes), data mesh (domains/products), data contracts, events.
- **Application SDK** (`atlanhq/application-sdk`) — separate Python framework for building connector apps/crawlers and App-Framework apps, container-first (Docker base images), used for both official and partner connectors.
- **REST API** underlies both SDKs; a **typedef toolkit** and CLI (`developer.atlan.com/sdks/cli/`) exist for schema/type management.
- **Webhooks**: "you can create webhooks that will send all metadata activity to a target URL of your choice" — pyatlan ships example handlers (incl. AWS Lambda) ([Event handling docs](https://docs.atlan.com/product/capabilities/build-apps/sdks/python/events/how-tos)). No public documentation of a raw Kafka-consumer interface for customers was found (internal eventing is presumably Kafka-based per Atlas heritage, but that surface is not exposed externally).
- **No official Terraform provider** was found — searches for `terraform-provider-atlan` return nothing; "governance as code" for Atlan today means pyatlan/CLI scripts and CI pipelines invoking typedef/policy APIs, not a first-party Terraform resource model. This is a real gap versus expectations from Snowflake/Databricks-native IaC teams.
- No public GraphQL API surfaced in this research pass; the Context Lakehouse marketing page claims "REST/Graph APIs" but no separate GraphQL endpoint documentation was located — needs direct confirmation with Atlan.

**Take/Leave:** Ship a Terraform/IaC provider for policy, typedef, and persona/purpose objects from day one — this is a gap Atlan still has in 2026, and a bank's platform team will demand governance-as-code before they'll adopt anything. The SDK + webhook model (typed SDK + outbound webhooks for metadata events) is a reasonable pattern to copy as-is.

## 10. Integrations

Connector categories per [atlan.com/connectors](https://atlan.com/connectors/): **Warehouses** (Snowflake, BigQuery, Redshift, Databricks — called out as the deepest/most-native integrations), **Databases** (Postgres, MySQL, Oracle, SQL Server), **BI** (Tableau, Power BI, Looker, Sigma), **ETL/ELT** (dbt, Fivetran, Matillion), **Orchestrators** (Airflow, Dagster), **Data Quality** (Monte Carlo, Anomalo, Bigeye, and via the App Framework: Soda, Great Expectations, Elementary, Qualytics). Native crawl scope: "structural context (databases, schemas, tables, views, columns with types/nullability), relationship-level lineage (upstream/downstream), operational context (row counts, last-modified, creation history)." Custom/long-tail connectors ("in days," per Atlan) are built on the open-source Application SDK. **Embedded collaboration**: Jira Cloud integration exists ([Integrate Jira Cloud](https://docs.atlan.com/product/integrations/project-management/jira/how-tos/integrate-jira-cloud)); a general [Integrations index](https://docs.atlan.com/product/integrations) and [FAQ](https://docs.atlan.com/tags/faq-integrations) exist, but Slack/Teams depth was not independently confirmed in this pass beyond the G2 complaint below (Teams integration issues). Treat "embedded collaboration" as a real but not deeply verified story — validate Slack/Teams request-and-approval workflows directly. *(2026-08-30 addendum: an independent practitioner review — see `90-reference/03-sources.md` → "Independent practitioner reviews" — corroborates that Atlan leads with this angle in its own positioning: it markets itself first as a data-team **collaboration hub** with Slack-native notifications and a Chrome extension over BI tools, not as a catalog portal you have to remember to open. That's still one secondary source, not primary-doc confirmation of workflow depth, but it does resolve the open question of *intent* — distribution into Slack/Chrome is a deliberate adoption strategy, not an incidental integration. We have no equivalent surface: our own UI (`ui/`) is a single-page portal nobody sees unless they open it — tracked as whitespace item W11 in `00-product/05-differentiation-and-whitespace.md`.)*

**Take/Leave:** Don't try to match Atlan's 100+ connector breadth — a bank platform has a small, known set of core systems (likely Snowflake/Databricks plus a handful of BI/orchestration tools). Go deep-native on those 3–5 and use an OpenLineage/plugin-SDK model for anything else, rather than building a broad shallow catalog.

## 11. Trust/quality

Atlan's own DQ capability, **Data Quality Studio**, launched for **Snowflake in private preview (June 2025)** running natively on **Snowflake Data Metric Functions (DMFs)** — rules execute inside the customer's Snowflake account (no separate infra), authored via no-code NL templates or custom SQL, producing real-time badges/scores/lineage overlays ([Businesswire launch](https://www.businesswire.com/news/home/20250603590536/en/Atlan-Launches-Data-Quality-Studio-for-Snowflake-Becoming-the-Unified-Trust-Engine-for-AI)). A **Databricks** version followed ([announcement](https://atlan.com/announcing-data-quality-studio-for-databricks/), [docs](https://docs.atlan.com/product/capabilities/governance/data-quality/databricks)). Atlan frames a **"Unified Trust Center"** that aggregates native DMF results *alongside* third-party partner signals — **Monte Carlo, Soda, Anomalo** explicitly named as ecosystem partners ([Monte Carlo/Atlan integration blog](https://www.montecarlodata.com/blog-scaling-data-trust-and-collaboration-with-monte-carlo-and-atlans-new-integration/)) rather than being replaced by the native studio. No GA date was found for Data Quality Studio as of the pages fetched — still described as preview/private-preview.

**Take/Leave:** Copy the "run DQ rules natively inside the warehouse, don't move data out" pattern (Snowflake DMF-style) directly — it minimizes data movement and audit surface, which matters enormously for a bank. Don't wait on building our own DQ engine before shipping; the aggregation-of-third-party-signals ("Unified Trust Center") pattern is a reasonable interim step while a native engine matures.

## 12. Weaknesses (from reviews and cross-source analysis)

- **Cost**: list prices for connectors and per-member licenses are "fairly high" versus comparable SaaS tools; real affordability depends on negotiated volume discounts, making Atlan best-suited to larger enterprises ([Praxi review](https://www.praxi.ai/honest-atlan-review-2025)). Third-party estimates put enterprise deals at $120K–$300K+/yr ([Vendr](https://www.vendr.com/marketplace/atlan)).
- **Personas/Purposes complexity**: powerful but confusing in practice — reviewers report needing to toggle between multiple screens to understand effective access, a steep learning curve especially for non-technical/business users ([Collate teardown](https://www.getcollate.io/learning-center/atlan-data-catalog)).
- **Setup/implementation effort**: full configuration (permissioning, governance workflows, lineage for non-native sources) "requires significant time, resources, and governance planning"; non-native database connections need extra infrastructure work.
- **Playbooks/automation gaps**: no undo, no per-asset impact report/notifications, no event-based automation triggers, no advanced approval workflows, and no manual lineage-editing UI.
- **Search**: performs poorly for exploratory/underspecified queries — "overwhelming or unclear results" when the user doesn't already know what they're looking for.
- **UI/UX**: G2 reviewers cite a steep learning curve, an interface felt "overly technical" rather than business-friendly, some screens lacking simple table views, and limited UI component customization.
- **Integration reliability**: Microsoft Teams integration issues and instability reported with Tableau/Matillion connections causing implementation delays; non-native DB connectivity requires extra infra ([G2 pros/cons](https://www.g2.com/products/atlan/reviews?qs=pros-and-cons)).
- **Support**: several reviews describe technical support as slow to resolve and "sometimes not very accurate."
- **No native adoption/usage reporting** beyond the built-in popularity metrics — orgs lean on third-party BI for deeper usage analytics.
- **Data Quality Studio is not yet GA** (private preview as of the material reviewed) — a bank building DQ-dependent governed-AI workflows should not assume production SLAs here yet.
- **No first-party Terraform provider** — "governance as code" must be hand-rolled via pyatlan/CLI, a gap versus infra teams expecting native IaC.
- **Auto-description quality**: Atlan is explicit that AI-generated descriptions/lineage explanations require human accept/reject/edit — i.e., Atlan itself does not claim unsupervised accuracy, which is a tacit admission of quality limits requiring workflow-level review gates.
- **Architecture story inconsistency**: current "Context Lakehouse" (Iceberg + knowledge graph + vector search) marketing does not reconcile with the previously-documented Cassandra/Elasticsearch/Postgres/Atlas-fork backend — worth pressing Atlan directly on which is production-true today vs. roadmap, especially for a regulated bank's architecture review.

## What to steal

- Typed-entity/supertype metadata model + custom-metadata attribute framework — proven, extensible, directly implementable (Atlas heritage).
- The Personas (catalog policy bundle) / Purposes (tag-based ABAC hard-deny) split, and specifically the **metadata-policy vs. data-policy separation of concerns** — the single best idea in the product for our use case.
- OpenLineage as the lineage-ingestion standard for Spark/Airflow — don't reinvent an event format.
- Popularity/usage scoring from warehouse query-log mining (`distinct_users × log(reads)`), cheap and effective.
- The metadata-only-to-LLM boundary plus mandatory human accept/reject on AI-generated content.
- Native in-warehouse DQ execution (Snowflake DMF-style) — no data egress, minimal new infra, smaller audit surface.
- Certificate states (Verified/Draft/Deprecated) and lineage-based tag/classification propagation.
- An App/connector SDK pattern for third-party and long-tail extensibility.
- MCP as the agent-interface protocol, with tool scoping and an explicit tool-restriction mechanism (`RESTRICTED_TOOLS`-equivalent).

## What to refuse

- Atlas/Cassandra/JanusGraph-class operational burden — pick a modern, well-operated storage stack instead of inheriting 2010s big-data ops complexity.
- Enforcing data-access policy only inside an app-layer gateway/query workspace — for an audited bank, access control must compile into the warehouse's native RBAC/RLS/masking so there is one inspectable source of truth, not two.
- An MCP tool that executes arbitrary live SQL (`query_asset`-equivalent) scoped only by a general-purpose API key's policy — too easy a path to scope creep or injection-driven overreach; needs a separate, tighter approval layer if built at all.
- Shipping automation/bulk-rules without undo, event triggers, and per-run impact reports — acceptable for a startup catalog, not acceptable for a bank's change-control and audit requirements.
- A loosely-specified, undocumented data-contract schema — ours must be versioned and machine-enforceable from the start.
- Chasing 100+ connector breadth — depth on the bank's actual core systems beats broad shallow coverage.
- Quote-only, opaque pricing and an unreconciled architecture story — both would fail a bank's procurement and architecture-review clarity bar; keep our own design docs honest about what's built vs. planned.
