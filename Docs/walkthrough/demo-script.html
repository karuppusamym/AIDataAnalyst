The maker-checker loop

Three identities, one governed change. Use it for Act 3's live path. Run in Windows PowerShell from any folder.

Writes: one glossary category, one glossary term and one review, all named demo_*, plus their audit events. They stay in the estate. Checked in-process, not on the live stack: tests/test_demo_maker_checker_loop.py sends these five steps to the real application with the same identities and asserts the statuses below, and fails if this script drifts from what it sends. It has not been run through PowerShell against the running estate, so dry-run it once first.
$api = "http://localhost:8000"; $org = "9b90b35f-dcf5-49d3-8f0e-2f269987ae87"
function As($user, $roles) { @{ "X-Principal-Id" = $user; "X-Roles" = $roles; "X-Organization-Id" = $org } }
function Call($method, $path, $who, $body) {
  $p = @{ Uri = "$api$path"; Method = $method; Headers = $who; ContentType = "application/json" }
  if ($body) { $p.Body = $body | ConvertTo-Json -Depth 8 }
  Invoke-RestMethod @p
}
$dana = As "dana.steward"  "DataSteward,MetadataReviewer,Analyst,Viewer"
$riya = As "riya.reviewer" "Reviewer,Viewer"
$omar = As "omar.auditor"  "Auditor,Viewer"
$stamp = Get-Date -Format "yyyyMMddHHmmss"

# 1. The maker proposes
$cat  = Call POST "/v1/organizations/$org/glossary-categories" $dana @{ category_key="demo_$stamp"; display_name="Demo $stamp"; description="Walkthrough demo"; parent_id=$null }
$term = Call POST "/v1/organizations/$org/glossary-terms" $dana @{ term_key="demo_term_$stamp"; display_name="Demo term $stamp"; definition="Created live to show maker and checker."; category_id=$cat.id; synonyms=@(); owner_principal="dana.steward" }
$review = Call POST "/v1/glossary-term-versions/$($term.id)/submit" $dana

# 2. The maker cannot approve her own change (expect 409)
try { Call POST "/v1/governance/reviews/$($review.id)/decision" $dana @{ decision="APPROVE"; reason="my own change" } } catch { "dana: HTTP " + $_.Exception.Response.StatusCode.value__ }

# 3. The auditor cannot decide at all (expect 403)
try { Call POST "/v1/governance/reviews/$($review.id)/decision" $omar @{ decision="APPROVE"; reason="auditor" } } catch { "omar: HTTP " + $_.Exception.Response.StatusCode.value__ }

# 4. The checker approves
Call POST "/v1/governance/reviews/$($review.id)/decision" $riya @{ decision="APPROVE"; reason="Independent check" }

# 5. The auditor reads what happened
(Call GET "/v1/organizations/$org/audit-events?limit=8" $omar).items | Format-Table occurred_at, principal_id, action, resource_type -AutoSize

Expected: step 2 prints dana: HTTP 409, step 3 prints omar: HTTP 403, step 4 succeeds, and step 5 lists the newest eight events. Four are this run's, by two principals: dana.steward (the category, the term and the submission) and riya.reviewer (the decision). Background workers write to the same ledger (checked live: fleet-scheduler, metadata-worker and auto-enqueue-drafter sit among the newest rows), so a few of the eight may be theirs; find your four by the term you just created. Omar never appears, and neither do the refused 409 and 403: a refusal and a read write no audit row, so the ledger records who changed something. Say that aloud; it is the honest reading of the ledger.

Do not show

  • Studio, Marketplace, Access policies, Delegations, Negative knowledge. They are empty on this estate.
  • Workspace access. It says the BI integration is disabled.
  • Any claim of WORM, alerting, HA, DR, scale or p95. The archive reports NO_ARCHIVES, there is no alert receiver, and none of the others has been measured.
  • Workspace authorization as enforced. It observes and records; it does not block yet.
  • The Engage button on the organization kill switch. Show the state; do not press it.
