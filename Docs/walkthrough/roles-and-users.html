Signing in as each user

A. Eight local UIs, one per user (quickest for a demo)

The shipped UI on :3001 bakes in a single identity (local-ui-admin, sixteen roles), so it cannot show two users. scripts/demo-users.ps1 starts one UI per user on its own port. Each sends that user's X-Principal-Id and X-Roles; the backend, not the browser, decides what is allowed.

.\scripts\demo-users.ps1                 # list the roster
.\scripts\demo-users.ps1 -Action Start   # start all eight, ports 5181-5188
.\scripts\demo-users.ps1 -Action Check   # confirm each serves its own identity
.\scripts\demo-users.ps1 -Action Stop
  1. Open the user's port, for example http://localhost:5183 for Riya.
  2. That is all. The UI opens as that user's persona in Northwind, set by the launcher (VITE_DEV_PERSONA, VITE_DEV_ORG_ID). Only alex and omar may list organizations, so most users have no picker; they do not need one.
  3. Before presenting, run the rehearsal: cd e2e; node scripts/demo-rehearsal.mjs. It opens every screen in each user's own menu from an empty browser and prints anything refused or broken.

The persona control still exists in this mode, and still only changes navigation. A browser that remembered a different organization earlier keeps it: clear the site data for that port.

This is the development identity provider. The API trusts X-Roles headers, which is how a local stack is meant to work and exactly why it must never face a network. Say so out loud, then show option C if the audience wants the production shape.
B. Straight at the API
curl -H "X-Principal-Id: riya.reviewer" -H "X-Roles: Reviewer,Viewer" \

Maker-checker is satisfied by sending a different X-Principal-Id for the approval.

C. OIDC, the production shape (mock issuer, dev only)

compose.oidc.yaml adds a real OIDC provider: signed tokens, a published key set, expiry, audience and issuer checks. It has no user directory, so you type each user's claims into its login form. Roles come from the roles claim through a closed mapping (an unmapped name grants nothing); persona comes from the groups claim and only picks navigation.

The six least-privilege bundles were added to the overlay for this walkthrough; before that only admin, steward and viewer existed, so a Reviewer, Auditor or Analyst could not be minted. Bring it up with docker compose -f compose.yaml -f compose.oidc.yaml up -d --build, from a clean worktree of HEAD. A ninth bundle, atlas-operations (Operations and Viewer), is defined for a platform runner who is not a PlatformAdmin; no demo user holds it, so type it by hand if you want to show one. A tenth, atlas-ingestor (MetadataIngestor only), is the push-only service account: no demo user holds it and it can read nothing.

What is proven, and what is not. tests/test_oidc_demo_bundles.py signs a token for each claim set above, sends it through the real verifier and asserts the roles, the persona and the organization that come out, and that an unmapped PlatformAdmin claim grants nothing. scripts/verify_oidc_bundles.py also signs in as every bundle through the mock issuer's login form (authorization code with PKCE) against a throwaway API from the checkout, and records /v1/me, one refusal and one admission for each: 11 of 11 checks passed on 2026-09-21 (ten bundles and an unmapped PlatformAdmin claim); against the code before R11-AUD01, 2 of 11 failed. Not driven: the compose api service in OIDC mode, and a real bank identity provider.

Know before you show

Roles are additive sets, not a ladder. Analyst is not a superset of Viewer: 68 routes admit Viewer and not Analyst (BI lineage, compliance packs, several governance reads). That is why every working user above also holds Viewer.
Persona is navigation, not permission. The dropdown changes the landing page and the checklist. It never changes which roles the request carries. Under OIDC it is derived from the groups claim and there is no dropdown.
Fixed 2026-09-21: every role a route guard names is now a role a token can carry. Nine names used to appear in guards without being in the catalog, so no OIDC token could carry them: ModelRiskManager (34 routes), DataProductOwner (25), DataScientist (18), DataEngineer (12), Steward (11), MetadataIngestor (9), ProjectAdmin (7), ComplianceOfficer (4) and DataConsumer (4). MetadataIngestor joined the catalog as a push-only role for the nine ingestion routes; Steward became DataSteward; the other seven were removed from the guards, always beside a grantable role, so nothing changed under OIDC. The compliance-pack routes now admit Auditor to list, read and download (generating a pack stays with PlatformAdmin and DataSteward). tests/test_guard_roles_are_grantable.py fails if a guard names a role outside the catalog. These are the recommendations the tracker row carried, applied on the product owner's instruction to proceed; the catalog is the product owner's to change.
Fixed while rehearsing: the Auditor's Policy refusals screen. It sat in the Auditor menu but its route admitted only DataAdmin and PlatformAdmin, so the Auditor saw a red error. The route now admits Auditor (read-only, tenant-checked) and a test pins it. Persona menus and role guards were written separately and nothing compares them; the rehearsal is what does.
Fixed since: the two quiet mismatches, and a third. The Developer's Context products screen no longer asks for ontology versions or routine options when the role may not read them, and the Home screen no longer asks non-reviewers for the review-queue summary. Both are gone from the rehearsal's known list. R11-AUD01 is closed: see the note above.
Maker is not checker, by principal id. A change's author cannot approve it, for any role including PlatformAdmin. That now includes the two access-control objects that used to break the pattern: creating an access policy and adding a workspace member (risk tier T3) each open a governance review. The policy is created as a draft and the member as pending, and neither takes effect until a different person holding PlatformAdmin, DataSteward or Reviewer approves it. An OrganizationAdmin can propose but cannot approve. Deployed 2026-09-21: the running API refuses a policy created ACTIVE with a 422. The approve loop is covered by in-process tests only.
Workspace-level access is observing, not enforcing. The role checks on this page are enforced. The finer workspace rules record what they would have decided and do not block yet.
Viewer alone is a refusal demo, not a working user. It cannot list organizations or load the scope picker, and the shell says exactly which roles are required. That is honest behaviour, and a good moment to show.
